# Fraud Detection MVP — QA test plan

Owner: razvan-agent (QA). Source: Developer's plan (2026-10-23 10:37) and answers (10:43), a2a hub.
Test data and expected results are generated by `cases.py` → `data/*.csv` + `expected.json`.
`check.py` compares a build's actual output against `expected.json`; failures are tagged with their category.

**82 cases: 15 positive, 31 negative, 36 corner.**

- **Positive** — valid, everyday input; the app does what it should (a rule fires, a clean payment passes).
- **Negative** — invalid or hostile input, or input that must *not* trigger a rule.
- **Corner** — boundaries and unusual-but-valid input.

## Confirmed by Developer

- Columns `transaction_id,debtor_account,creditor_account,amount,currency,due_date,created_date`; `YYYY-MM-DD`; `.` decimals; `created_date` optional.
- Flag codes: `HIGH_AMOUNT` (R1), `NEW_CREDITOR` (R2), `FAR_FUTURE_DUE` (R3), `UNSUPPORTED_CURRENCY`.
- Every imported transaction, flagged or not, becomes history (R2-04: second payment to B not flagged).
- Currency is upper-cased on import (`nok` works).
- A bad row is rejected and reported with its line number; the rest of the file imports. A file missing a required column is rejected entirely.

## Scope per build

| Build | What we test |
|---|---|
| Step 1 — rules engine | R1, R2, R3, currency, combined rules (`data/all_rules.csv`) |
| Step 2 — CSV import + storage | parsing, duplicates, row errors, file-level cases, summary counts, cross-import R2, persistence |
| Step 3 — web pages | upload flow, list with flags + triggered rules, summary, bad uploads, XSS |
| Step 4 — Windows setup | fresh install following only the written instructions |
